# Bongsu Architecture

Bongsu means "봉수대": a watchtower network that sends signals from the edge back to a central point. The system follows that model.

## Goals

- Collect host and running-container package inventories with Trivy and optional osquery.
- Send SBOM-like package data to the central server with host, OS, container, image, and runtime context.
- Build and maintain a merged security database from public sources such as CISA KEV, FIRST EPSS, OSV, NVD, and Trivy DB.
- Support connected and air-gapped deployments. Connected sites update every 6 hours; air-gapped sites import exported data.
- Separate OS package advisories from code library advisories.
- Provide a web dashboard, one-line agent install, force scan requests, and an RBAC-ready data model.

## Current Implementation

- Server: Go static binary, PostgreSQL, Vite dashboard, Docker Compose deployment.
- Agent: Go static binary. It collects host metadata, users, processes, listening ports, host packages, and running Docker container packages.
- Auth: admin APIs use `BONGSU_API_KEY`; agent report and force-scan polling use `BONGSU_AGENT_API_KEY`; installer generation requires `BONGSU_INSTALL_TOKEN`; binary downloads accept that token or an admin API key header; viewer keys from `BONGSU_VIEWER_API_KEYS` are scoped through RBAC policies. Server startup rejects missing, placeholder, short, or duplicate admin/agent/install secrets unless `BONGSU_ALLOW_WEAK_SECRETS=true` is explicitly set for development. Agents also present a persistent per-host token through `X-Bongsu-Agent-Token` and `X-Bongsu-Host-ID`; with `BONGSU_AGENT_HOST_BINDING=true` the server stores only the token hash and rejects later reports, claims, or completions for the same host when the token does not match. Admins can reset a host's bound token through `/api/hosts/{id}/agent-token/reset` when a host is reinstalled or loses local state; the next valid agent check-in binds the replacement token and the reset is audited. Browser CORS is same-origin by default and only reflects origins listed in `BONGSU_CORS_ALLOWED_ORIGINS`. Browser-facing responses set defensive headers including `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, a same-origin Content Security Policy, and a restrictive `Permissions-Policy`; HTTPS or `X-Forwarded-Proto=https` responses also set HSTS unless `BONGSU_HSTS_ENABLED=false`. API responses default to `Cache-Control: no-store`, `Pragma: no-cache`, and `Expires: 0` so host inventory, SBOM, vulnerability, RBAC, and audit data are not retained by browser or intermediary caches. Every HTTP response carries an `X-Request-ID`, preserving a valid inbound ID or generating one, and audit metadata records the same request ID for operator correlation. Access logs include request ID, method, path, status, bytes, duration, and client IP when `BONGSU_ACCESS_LOG=true`; `/api/health` is skipped unless `BONGSU_ACCESS_LOG_HEALTH=true`. The HTTP server sets configurable request header read, full request read, response write, idle, and max header limits through `BONGSU_HTTP_*` settings. PostgreSQL pool size and connection lifetime are configurable with `BONGSU_DB_MAX_OPEN_CONNS`, `BONGSU_DB_MAX_IDLE_CONNS`, and `BONGSU_DB_CONN_MAX_LIFETIME_MINUTES`. The generated one-line installer and packaged `scripts/install-agent.sh` render credentials safely, use fail-fast header-authenticated binary downloads instead of token-bearing download URLs, verify downloaded binaries against the server's `X-Bongsu-SHA256` header, generate or reuse a persistent `agent.token`, and write it into `config.yaml`; the generated installer also returns `Cache-Control: no-store`.
- Matching: packages-only mode sends packages to the server, then the server runs Trivy SBOM matching with the local Trivy DB. Server-side matching writes transient SBOM input through private `0600` temporary files and removes them after Trivy returns, so package inventories are not exposed through predictable shared temp paths.
- Security DB: JSONL import/export for `cve_database`, Trivy DB upload/update, source sync command hook via `BONGSU_SECURITY_DB_SYNC_CMD`.
- Airgap: server can import CVE JSONL and Trivy DB archives. The one-line installer downloads the agent and Trivy binaries from the management server.
- Data model: host, scan, package, vulnerability, container asset, security source, scan request, and RBAC policy tables.

## Security Sources

Security sources are classified into:

- `os-package`: Debian, Ubuntu, Alpine, RHEL-family, SUSE, Wolfi/Chainguard, and similar distribution advisories.
- `code-library`: PyPI, npm, Go, Maven, crates.io, NuGet, RubyGems, Packagist, and similar language ecosystems.
- `general-cve`: NVD/CPE-oriented records and priority feeds such as CISA KEV and FIRST EPSS that may enrich either category.
- `custom`: locally imported or future proprietary feeds.

The merge strategy is:

1. Normalize source records into `cve_database`; the bundled connected sync imports CISA KEV, FIRST EPSS, OSV, NVD, and Trivy-derived records.
2. Keep source provenance in `source`, `category`, `ecosystem`, `raw_data`, and timestamps.
3. Prefer stronger CVSS scores/vectors and fixed-version data when enriching scan findings; fixed-version enrichment reads both top-level fixed lists and fixed events inside affected ranges.
4. Match by ecosystem-aware identity first. Name-only candidates are discarded unless `affected_products` contains the same package name, compatible ecosystem/category, fixed-version data, and an affected range that contains the installed version. Fixed versions can come from either the advisory's top-level `fixed` list or fixed events inside range data, and multiple introduced/fixed intervals in one range are evaluated independently.
5. CVSS vectors are recalculated after import for supported CVSS v2, v3.x, and v4.0 formats.
6. CISA KEV and FIRST EPSS records are kept as separate `cisa-kev` and `epss` sources and do not create name-only package matches by themselves. Instead, vulnerability list/detail/export responses mark an existing finding as `exploited=true` when the same CVE appears in the KEV feed and attach `epss_score`/`epss_percentile` when EPSS has scored the CVE. Findings also expose a computed `risk_score` from CVSS, EPSS probability, KEV membership, and host criticality plus a `risk_level` bucket (`critical` >= 80, `high` >= 60, `medium` >= 40, otherwise `low`) so the default remediation queue sorts by practical operational priority instead of raw scanner severity alone.
7. `/api/cve-db/stats` reports the generated timestamp, `security_db_revision`, source count, total records, total matchable records, source quality counters for ecosystem metadata, fixed versions, affected ranges, CVSS data, matchable records, and `matchable_percent` so operators can reject weak feeds before they create noisy matches. `matchable` requires package name, ecosystem context, and fixed-version data, counting fixed events inside affected ranges but not range metadata that lacks a fixed event. The same response includes the active rematch policy from `BONGSU_CVE_MATCH_SOURCES`, `BONGSU_CVE_MATCH_MIN_SOURCE_MATCHABLE_PERCENT`, and `BONGSU_CVE_MATCH_CANDIDATE_LIMIT`, plus per-source `rematch_eligible` and exclusion reasons. The dashboard shows CVE DB status, revision, total records, matchable percentage, weakest source, rematch-eligible source count, stale source count, policy-excluded sources, and highlights sources below the selected minimum matchable percentage before rematching.
8. Rematch can be constrained by source allowlist and minimum matchable percentage through `BONGSU_CVE_MATCH_SOURCES`, `BONGSU_CVE_MATCH_MIN_SOURCE_MATCHABLE_PERCENT`, or the dashboard rematch control. Candidate evaluation is bounded by `BONGSU_CVE_MATCH_CANDIDATE_LIMIT` (default 50000, maximum 1000000); rematch results and audit metadata set `limited=true` when that boundary is reached so large environments do not mistake a partial candidate pass for a complete one.

Scanner package ecosystems are kept distro-specific for OS advisories. For example, Trivy `ubuntu` packages are stored as `Ubuntu` rather than collapsed into `Debian`, so Ubuntu advisories can match without weakening Debian/Ubuntu separation.
Version comparisons treat pre-release markers such as `alpha`, `beta`, and `rc` as lower than the corresponding final release so release candidates are not incorrectly considered fixed.
Scanner-imported vulnerabilities are bound back to packages by scanner target and package name, with name-only fallback only when the package name is unique in the scan. This avoids linking same-named packages from different ecosystems or manifests to the wrong package row.
Vulnerability inserts drop dangling scanner rows that have no package, scan, host, or vulnerability identity instead of letting one malformed row discard the whole batch. Trivy vulnerability rows are bound to package rows by target, package name, and installed version before falling back to unambiguous package-name matches, so duplicate package names in one lockfile/image do not attach findings to the wrong version. Report ingest also applies a scan-scoped CVE DB rematch after package persistence, so automatic package-only rescans keep OSV/NVD/custom advisory findings on the newly reported latest scan instead of only on the previous inventory. Report audit metadata records inserted and skipped vulnerability counts plus table-level ingest errors. Agents also upload bounded collection errors for partial host, container, Trivy, or osquery failures, and the server folds those into the same ingest-error channel. Scans with skipped vulnerability rows, agent collection errors, or partial inventory persistence failures are stored, audited, and webhooked with `degraded` status so operators can filter for scanner output quality issues while still using the scan as the latest inventory. `/api/report` trims scanner identity fields, requires supplied scan IDs to be UUIDs, accepts only known scan types, derives stable host fallback IDs, and rejects oversized JSON bodies before decode with a `413` response; `BONGSU_AGENT_REPORT_MAX_BYTES` controls the limit and defaults to 536870912 bytes. Large security DB upload surfaces also use explicit operator-tunable body limits: `BONGSU_TRIVY_DB_UPLOAD_MAX_BYTES`, `BONGSU_CVE_DB_IMPORT_MAX_BYTES`, and `BONGSU_SECURITY_DB_BUNDLE_MAX_BYTES`. Multipart parsing uses the separate `BONGSU_MULTIPART_MEMORY_MAX_BYTES` threshold so large uploads spill to temporary files instead of being held in memory up to the full body limit. Control-plane JSON APIs such as host metadata, triage, scan requests, retention, rematch options, and RBAC mutations use `BONGSU_JSON_BODY_MAX_BYTES` (default 1048576) and return `413` before decode when that limit is exceeded.

## Connected Update Flow

1. Server has `BONGSU_SECURITY_DB_SYNC_CMD` configured, usually:
   `scripts/sync-all-cvedb.sh http://localhost:5677` with `BONGSU_API_KEY` available in the environment.
2. In connected docker-compose, the server starts listening first, runs the configured source sync once on startup by default, and then runs it every `BONGSU_SECURITY_DB_INTERVAL_HOURS`, default 6.
3. Scripts download CISA KEV, FIRST EPSS, OSV, NVD, and Trivy-derived metadata, then import JSONL through `/api/admin/cve-db/import`; import HTTP errors, malformed responses, empty mandatory source output, incomplete NVD year downloads, and required Trivy extraction failures are fail-closed so the periodic sync is marked failed instead of silently publishing a partial source set. The Trivy extraction step searches `TRIVY_BIN`, `BONGSU_TRIVY_PATH`, `/opt/bongsu/bin/trivy`, and bundled binary paths before declaring the source unavailable, and source download work directories can be moved off small `/tmp` filesystems with `BONGSU_TMPDIR`. CVE source IDs are canonical lowercase slugs (`a-z`, digits, dot, underscore, hyphen; max 64 chars) before source-level replacement, so `OSV` and `osv` cannot drift into separate feeds. CVE entry identity fields, source metadata, CVSS vectors, titles, descriptions, and severity casing are normalized during import before filtering and upsert, so feed whitespace or lowercase severity does not create duplicate or weakly classified records. The NVD importer combines all downloaded years and replaces the `nvd` source once, preserving the existing NVD source if any year fails. The security DB manager retains a bounded tail of the latest sync output, controlled by `BONGSU_SECURITY_DB_SYNC_OUTPUT_MAX_BYTES`, for admin-authenticated health checks and failed update responses; unauthenticated health checks expose only summary sync status, last successful sync, last attempt, next scheduled sync, and interval. Trivy DB health also reports ready/status/last-update summary publicly and includes the latest bounded download/load error only for admin-authenticated health checks. `/api/health` also exposes merged source freshness using `BONGSU_SECURITY_DB_MAX_SOURCE_AGE_HOURS` (default 30) and marks the DB degraded when any source in `BONGSU_SECURITY_DB_REQUIRED_SOURCES` is absent (default `cisa-kev,epss,osv,nvd,trivy`), plus security recalculation `running` and `pending` flags and the latest completed/error recalculation audit summary, with freshness errors, recalculation errors, and the pending reason available only to admins, so operators can distinguish an idle DB from a stale, incomplete source DB or a background CVSS/enrichment/rematch pass that has not yet queued rescans.
4. Each successful DB change, including periodic security DB sync, starts background CVSS recalculation, vulnerability enrichment, stale CVE DB rematch cleanup, CVE rematching, and then automatic package-only rescan requests for hosts seen within `BONGSU_AUTO_RESCAN_LAST_SEEN_HOURS` (default 720). Recalculation runs as a serialized background worker: if CISA KEV, EPSS, OSV, NVD, and Trivy imports arrive while a pass is still running, bongsu queues one follow-up pass instead of running overlapping recalculations. Auto-rescan audit metadata records the recalculation status that preceded queueing.
5. Operators export `/api/admin/security-db/export` for air-gapped transfer. The bundle contains a manifest, CVE JSONL, source stats, and optionally the current Trivy DB archive.

Database migrations are tracked in `schema_migrations` with per-file SHA-256 checksums. Startup applies each SQL migration once, records the checksum transactionally with the migration, skips already-applied files on later restarts, and refuses to start if an applied migration file is modified in place. When upgrading a legacy database that already has the current table, column, and conflict-index schema markers but no migration ledger, startup baselines the bundled migration files into `schema_migrations` without rerunning their SQL; older partial schemas continue through the normal idempotent migration path. This keeps cleanup and requeue migrations from repeating on every container restart and gives operators a deterministic upgrade trail.

## Air-Gapped Flow

1. In a connected environment, build Docker images and static binaries.
2. Download/update Trivy DB and CVE JSONL exports.
3. Transfer images, binaries, Trivy DB archive, and CVE JSONL into the air-gapped network.
4. Start Docker Compose without online DB updates.
5. Import Trivy DB through `/api/admin/trivy-db`.
6. Import CVE JSONL through `/api/admin/cve-db/import`.

The implemented bundle is a versioned `tar.gz` archive containing `manifest.json`, `cve-database.jsonl`, checksums, source stats, `security_db_revision`, and optional `trivy-db.tar.gz`. Bundle export first materializes the complete archive to a temporary file and closes the tar/gzip writers before returning response headers, so archive construction errors do not create partial successful downloads. Import rejects unexpected, non-regular, or duplicate tar members, stages payloads to temporary files, verifies manifest SHA-256 checksums, and confirms the manifest CVE record count matches the imported valid rows before mutating the CVE database or Trivy cache. After validation, importing the bundle validates any Trivy archive without activation, replaces the full CVE database inside one database transaction, commits that transaction, then activates the staged Trivy DB and triggers background CVSS/enrichment/rematch recalculation plus automatic package-only rescans. The dashboard exposes admin bundle export/import controls with an `include_trivy` option so connected and air-gapped operators can perform the transfer without shell access. Export and import audit metadata records the manifest security DB revision so offline transfer logs can be correlated with the automatic rescan revision. `/health` and the dashboard expose the current merged `security_db_revision` and source freshness; revision and freshness lookup errors are shown only to admins. Trivy DB extraction rejects unsafe paths and unsupported entry types before activation. Direct CVE JSONL imports through `/api/admin/cve-db/import` use the same all-or-nothing transaction boundary, replace existing rows for the imported source, reject malformed or empty JSONL as a client error, and audit failed attempts. Successful direct CVE JSONL import responses and import/export/rematch/CVSS recalculation audit rows also include the resulting `security_db_revision`. CVE JSONL export first materializes a complete temporary file, including source-filtered exports, so row scan or encode errors fail before returning a partial download; the response includes content length, record count, SHA-256, and security DB revision headers for transfer verification. Any CVE row insert error rejects the entire CVE payload instead of committing a partially corrupt source update, and an invalid Trivy archive does not overwrite the existing Trivy cache.

## Force Scan Model

The server stores force scan requests in `scan_requests`. The intended lifecycle is:

- `pending`: a user or automation requested a scan.
- `claimed`: an agent picked up the request.
- `completed`, `degraded`, or `failed`: the agent submitted a clean result, submitted a partial/degraded result, or reported failure.

Current implementation exposes request creation/listing/cancel/requeue plus agent claim/complete endpoints. Agents can run with `--daemon --poll-interval 60s` to claim pending requests, execute a scan, upload the report, and mark the request completed, degraded, or failed based on the server's persisted scan status. Admin-created scan requests are normalized to a fresh `pending` state, and host-targeted requests must reference an existing host so typos do not create permanently unclaimable work. Claiming a request records `claimed_by_host_id`; agent completion must include the same host ID and is rejected if a different host tries to complete the request. Completion and requeue messages are trimmed and UTF-8 safely bounded before they are written to the database or audit log, so a failed agent cannot flood scan history with unbounded process output. Admin cancellation still works for pending or claimed rows, while missing requests return `404`, and already terminal requests return `409` instead of creating misleading success audit rows. Failed, degraded, or cancelled scan requests can be requeued individually or in bulk from Scan History, which clears claim/completion fields and preserves target host, scan type, package-only mode, reason, and security DB revision for retry. Bulk requeue requires at least one filter, only acts on failed, degraded, or cancelled requests, and prompts with the active filter set before execution so admins cannot accidentally reset all operational history. Scan request list responses include request age, claim age, and stale booleans derived from `BONGSU_SCAN_REQUEST_CLAIM_TIMEOUT_MINUTES`; the list API also accepts `stale=true` to return only pending or claimed work older than that same timeout. Scan History uses those stale flags instead of a client-side fixed threshold so operators can identify stuck agents before retrying. Claimed requests older than `BONGSU_SCAN_REQUEST_CLAIM_TIMEOUT_MINUTES` are requeued automatically during agent claim and can also be requeued by admins from the Scan History view; requeue clears the claimed host ownership. Stale requeue also cancels duplicate stale claimed `security-db-update` rows when a newer pending or claimed automatic rescan exists, and both API responses and audit metadata report `cancelled_duplicates` so operators can explain automatic backlog cleanup. Security DB updates enqueue `security-db-update` scan requests automatically after the corresponding recalculation pass. Those requests store a `security_db_revision`, a stable short hash derived from CVE source quality counters and source update timestamps, so operators can prove which DB generation caused a pending, claimed, completed, degraded, or failed automatic rescan. Dashboard stats separately expose pending, claimed, degraded, and failed `security-db-update` request counts for the current revision, plus RBAC-scoped stale pending and stale claimed request counts; the stale cards open Scan History with `stale=true` and status filters pre-applied. `/api/admin/metrics` exposes the same stale pending/claimed scan request backlog as `bongsu_scan_request_stale{state=...}` for alerting. Current DB rescan cards open Scan History with status, scan type, and revision filters pre-applied so operators can inspect the exact backlog without mixing in manual or daily scan requests. Claim, completion, failure, cancellation, and requeue audit metadata carries the request type, target host, claimed host, package-only mode, reason, and security DB revision. The request list API and Scan History view can filter by status, scan type, security DB revision, and stale status, allowing operators to isolate automatic rescans for one DB generation or stuck scan work. Only pending automatic rescans are deduplicated per host; a duplicate pending request is updated to the latest revision instead of keeping stale provenance, and if a new CVE DB update lands while a previous automatic rescan is already claimed, bongsu still leaves a follow-up pending rescan for the newer DB contents. Manual or unrelated active scan requests do not suppress the follow-up security DB rescan. Auto-rescan queue results are written to audit logs as `security_db.auto_rescan`, including eligible host count, queued request count, already pending request count, recalculation status, security DB revision, disabled cases, and error cases. Viewer access to scan request queues is host-scoped through RBAC; global all-host requests remain visible only to admins.

## Container Inventory

Running container metadata is stored separately from package rows in `container_assets`. The inventory preserves host ID, runtime, container instance ID/name, image name, image ID/digest, state, labels, and start time. `/api/containers` returns the latest completed or degraded scan per host and supports host, runtime, state, image, name, container ID, and image ID filters. Container rows include package count, actionable vulnerability count, critical/high counts, and max CVSS for that container in the latest scan, and the dashboard can sort by those fields so image risk triage does not require pivoting through package or CVE tables first. Viewer RBAC is applied before returning rows and before returning package/vulnerability filter options, so container names, package sources, package types, and host IDs are not exposed outside the viewer's allowed host scope.

## Scan Inventory Drift

`/api/scans` includes package, vulnerability, and container counts for each scan plus package inventory delta against the previous completed or degraded scan for the same host. Delta identity uses asset/source/container/package metadata without the version field, so version movement is reported as `packages_changed`, while new or missing identities are reported as added/removed. Degraded scans persist a bounded `error_summary` derived from agent collection and ingest errors, and the Scan History dashboard exposes it beside scan status so operators can spot broken collectors, unexpected package churn, container image drift, or partial persistence failures without pivoting into audit logs first.

## Asset Metadata

Hosts preserve operator-owned metadata independently from agent reports: owner, team, environment, criticality, and JSON tags. Agent check-ins update technical facts such as OS, IP, CPU, and memory without overwriting this metadata. Agents normally send a stable host ID derived from machine-id or hostname; if an older or malformed report omits it, the server derives a stable fallback from hostname or IP before using a random ID as the last resort. Admins can update metadata through `/api/hosts/{id}/metadata`, the dashboard shows it on host inventory/detail pages, and CycloneDX SBOM exports include it as `bongsu:*` root component properties.

Agent status is derived from each host's `last_seen` timestamp at read time. The dashboard and `/api/hosts?agent_status=...` expose `online`, `stale`, `offline`, or `unknown`; defaults mark agents online for 26 hours and offline after 72 hours, controlled by `BONGSU_AGENT_ONLINE_MINUTES` and `BONGSU_AGENT_OFFLINE_MINUTES`. `/api/admin/metrics` also exposes agent fleet counts by status and reported agent version so operators can alert on stale/offline coverage gaps and detect partial rollouts.

Agent check-ins bind a per-host agent token hash on first report and reject later reports for that host when the token hash does not match. Host list/detail responses expose only `agent_token_set` so operators can see whether the host is bound or waiting for a reset/rebind without leaking the stored hash. Admins can reset a host's token binding from the dashboard; the next valid check-in binds a new token and the reset is audited.

Host list responses include `latest_inventory`, summarizing the latest completed or degraded scan ID, scan status, finish time, package count, vulnerability count, and container count. They also include `active_vuln_counts`, the same latest-scan remediation finding counts used by the dashboard. This gives operators a quick signal for stale agents that are checking in but producing empty or incomplete SBOM data. `/api/hosts?inventory_status=...` supports `healthy`, `degraded`, `stale`, `empty`, and `none`; `stale` is controlled by `BONGSU_INVENTORY_STALE_HOURS` and defaults to 48 hours. The dashboard uses the same filtered API to show RBAC-scoped SBOM health counts, and the agent/SBOM health cards open the host list with the corresponding status filter pre-applied for operational follow-up. `/api/admin/metrics` exposes fleet-wide inventory status counts plus latest package/vulnerability/container totals. `/api/stats` also includes RBAC-scoped agent status counts, inventory status counts, SBOM coverage percentage for hosts with any usable completed/degraded inventory, a separate fresh-inventory percentage for healthy/degraded non-stale inventories, latest inventory package/vulnerability/container totals, and active finding counts from each host's latest completed or degraded scan, excluding terminal triage states, fixed rows, no-fix rows, CGA rows, hash-only fixed versions, and ecosystem mismatches. Scan request status counts are included so operators can see pending, claimed, and failed force-scan or automatic rescan backlog from the first dashboard view.

Dashboard summary views group active remediation findings by `owner`, `team`, `environment`, and `criticality` through `/api/vuln-summary?group_by=...`. The summary is RBAC-scoped and uses the same latest-scan active finding filter as `/api/stats` and `/api/hosts`, including total, risk bucket, severity, and SLA-overdue counts so remediation queues can be routed by operational ownership. Summary rows open the vulnerability queue with the matching owner/team/environment/criticality filter, and risk/overdue cells add the corresponding risk or SLA filter for direct triage. The vulnerability queue shows active filter chips and a single clear action so operators can confirm and reset drill-down context before exporting or triaging.

## RBAC Model

RBAC tables are present:

- `access_subjects`: future users and groups from company identity systems.
- `access_policies`: `read`, `export`, `write`, or `admin` permissions on `host`, `container`, `image`, `asset_group`, or `all`.

Runtime RBAC supports viewer API keys mapped to external subjects through `BONGSU_VIEWER_API_KEYS=key:subject`, with typed subject refs such as `key:user:alice` or `key:group:platform` when user and group IDs may overlap. Untyped `key:alice` remains supported for simple deployments. Admins create, list, and delete `access_subjects` and `access_policies` through `/api/admin/rbac/*` or the dashboard RBAC view; viewer queries are scoped to allowed hosts across host, package, vulnerability, scan, filter-option, and stats views. Export endpoints require `export` or `admin` permission and do not become public when `BONGSU_WEB_AUTH=false`, so read-only dashboard access cannot silently become bulk SBOM or vulnerability data exfiltration. Deleting a subject revokes all attached policies through database cascade. Policy creation accepts a subject UUID, a typed external ID, or an untyped external ID only when it resolves to exactly one subject; the dashboard uses UUIDs to avoid ambiguity when a user and group share the same external ID. Policy creation requires a known subject so typos do not silently create ineffective access grants. Future SSO integration should replace static viewer keys with identity-provider subjects.

RBAC resource matching supports:

- `all:*`: read every resource.
- `host:<host_id>`: read one host and its packages, vulnerabilities, scans, SBOM, and containers.
- `container:<container_id_or_name>`: resolve the latest matching container asset to its host scope.
- `image:<image_name_or_id_or_digest>`: resolve the latest matching image asset to its host scope.
- `asset_group:<selector>`: resolve hosts by operator metadata. Supported selectors are `owner:<value>`, `team:<value>`, `environment:<value>`, `criticality:<value>`, and `tag:<key>=<value>`.

Container and image policies are resolved from the latest completed or degraded scan per host so access follows the current runtime inventory instead of stale historical scans. Asset group policies are resolved from current host metadata so ownership transfers or environment changes immediately affect viewer scope.

## Audit Trail

Administration and agent events are written to append-only `audit_logs` rows. The current audit surface includes installer generation and binary downloads, agent report submissions, force-scan request lifecycle events, scan deletion, SBOM export, vulnerability report export, Trivy DB upload/update, security DB import/export/update, CVE DB import/export/rematch/CVSS recalculation, serialized security recalculation worker events, auto-rescan queue results, vulnerability triage changes, RBAC subject/policy changes and deletions, webhook delivery results, and periodic security DB change hooks. Security DB sync command failures, including failed manual updates and failed periodic syncs, are audited with `status=error` and the bounded command error captured by the sync manager. Security DB bundle import failures are audited with `status=error` and a stage name, so corrupt, tampered, or operationally incompatible airgap bundles remain traceable. Recalculation audit metadata includes CVSS, enrichment, rematch, stale-rematch cleanup, and severity-normalization counts; partial worker failures are recorded with `status=error` and step-level error messages instead of being reported as successful. The latest non-queued/non-started recalculation audit entry is summarized on `/api/health`, the dashboard, and `/api/admin/metrics`, including rematch candidate-limit hits, so operators can alert on a failed or partial background pass without manually opening audit logs. Manual scan deletion protects each host's latest completed or degraded inventory scan unless admins explicitly use `force=true`; forced deletes are recorded in audit metadata, and missing scan IDs return `404` instead of creating misleading success audit rows. Admins can query `/api/admin/audit-logs` with `actor_type`, `actor_id`, `action`, `resource_type`, `resource_id`, `status`, `created_from`, `created_to`, `limit`, and `offset`; date-only audit ranges use `YYYY-MM-DD` and `created_to` includes the full selected day. The dashboard exposes the same data in the Audit Log view for operational review, and the CVE source table marks stale sources with per-source age alongside matchability and rematch policy warnings so operators can identify the exact feed behind a degraded security DB state. `/api/admin/metrics` exposes Prometheus-compatible text metrics for PostgreSQL pool health, agent status/version coverage, SBOM inventory quality, security DB sync schedule and failures, security DB recalculation state and latest result, Trivy DB readiness, source freshness/staleness, source matchability quality, rematch policy eligibility per source, active vulnerability risk-level backlog, overdue SLA risk-level backlog, the current security DB revision, and automatic rescan backlog; it requires the admin API key.

## Retention

Admins can dry-run or execute `/api/admin/retention/prune` from the dashboard to remove old operational history. The prune action deletes terminal scans older than `BONGSU_RETENTION_SCAN_DAYS` while preserving each host's latest completed or degraded scan; running scans are not pruning targets. It also removes completed/degraded/failed/cancelled scan requests older than `BONGSU_RETENTION_SCAN_REQUEST_DAYS`, and removes audit events older than `BONGSU_RETENTION_AUDIT_DAYS`. Retention responses, dashboard messages, and audit metadata include the effective scan/request/audit cutoff timestamps plus deleted scan, package, vulnerability, container, user, process, port, scan-request, and audit-log counts so operators can review and reproduce the full blast radius. Triage decisions and the current host inventory are not pruned by this action.

## Vulnerability Triage

Triage decisions are stored separately from scan-result rows in `vulnerability_triage`, so they survive rescans and security DB updates. A decision can target one CVE globally, one CVE on a host, or one CVE/package pair on a host; package-scoped decisions require a host so exceptions cannot accidentally become global package-name rules. Current statuses are `open`, `in_progress`, `accepted_risk`, `false_positive`, `fixed`, and `ignored`; `accepted_risk`, `false_positive`, `fixed`, and `ignored` require a reason before they can be saved because they can suppress remediation queues. Expired decisions stop applying automatically. The dashboard exposes an expiry date for time-bound exceptions, exports include `triage_expires_at`, and triage changes are audited through `vulnerability.triage`. Admin `/api/stats` responses expose active, expired, and expiring-soon triage counts for dashboard exception lifecycle cards. `/api/admin/metrics` exposes active/expired triage decision counts and expiring-soon counts; `BONGSU_TRIAGE_EXPIRING_SOON_DAYS` controls the warning window and defaults to 14 days.

## Remediation SLA

Findings expose computed SLA fields from first-seen time and severity: `sla_days`, `due_at`, and `overdue`. Defaults are 7 days for critical, 30 for high, 90 for medium, and 180 for low, controlled by `BONGSU_SLA_*_DAYS`. SLA overdue filtering excludes triaged `accepted_risk`, `false_positive`, `fixed`, and `ignored` findings so accepted exceptions do not pollute operational breach queues. `/api/stats` exposes RBAC-scoped `overdue_sla_count` and `overdue_sla_risk_counts`, and the dashboard links those cards directly into the overdue vulnerability queue.

## SBOM Export

Each host can export its latest completed or degraded package inventory as CycloneDX 1.5 JSON through `/api/hosts/{id}/sbom` or SPDX 2.3 JSON through `/api/hosts/{id}/sbom?format=spdx`. Exports include bongsu host/package context such as host ID, scan ID, OS, asset type, container/image identifiers, source, package type, ecosystem, file path, and target. CycloneDX component `bom-ref` values are stable bongsu identities based on package placement context instead of raw purl strings, so the same package/version appearing in multiple containers remains reference-safe; the host root component also lists package components through CycloneDX `dependencies` and includes a deterministic scan-derived `serialNumber`. SPDX packages include purl external references, deterministic package verification codes based on stable package identity rather than database row IDs, sanitized document names/namespaces derived from host and scan identity, and explicit `NOASSERTION` license/copyright/supplier fields when the scanner did not collect authoritative values. Viewer RBAC requires `export` or `admin` permission before export, and export attempts are audited before bytes leave the service with follow-up success or error audit rows.

## Vulnerability Report Export

Filtered vulnerability and package views are always scoped to each host's latest completed or degraded scan, including when a specific `host_id` filter is used. Package `max_cvss`, `vuln_count`, and package vulnerability details use the same active finding filter as the remediation dashboard. Vulnerability rows include package type, ecosystem, asset type, container ID, image name/ID, and target from the matched package row, so operators can distinguish OS package findings from language-library findings while reviewing matches and exports and can route container image remediation without manually joining package inventory. Vulnerability rows also expose `advisory_sources`, the non-priority CVE DB feeds that contain the same CVE, affected package name, compatible ecosystem, and fixed-version data, so operators can see whether a finding is backed by OSV, NVD, Trivy-derived metadata, or another imported feed while avoiding provenance from a same-named package in a different ecosystem. Vulnerability findings are unique per package, scan, and vulnerability ID; migrations deduplicate older rows by keeping the strongest CVSS/fixed-version candidate, and scanner/rematch inserts ignore duplicate conflicts. Findings record `finding_source`, defaulting to `scanner`; CVE DB rematch inserts use `cve-db`, which lets security DB recalculation remove stale rematch-only findings without deleting scanner-reported findings. Operators can filter vulnerability views and exports by `finding_source` to isolate scanner findings from CVE DB rematch findings; the API accepts only `scanner` or `cve-db` for that filter so typoed source names fail fast instead of silently producing misleading queues. Findings also carry `risk_score`, `risk_level`, `exploited`, `epss_score`, and `epss_percentile` priority signals derived from CVSS, CISA KEV, FIRST EPSS, and host criticality; list/export filters accept `risk_level`, `exploited=true`, `min_epss`, and `min_epss_percentile` for risk-focused remediation queues without allowing priority-only source records to create package-name matches on their own. `/api/stats` and grouped `/api/vuln-summary` responses include active risk-level counts, so dashboards can prioritize owner and environment queues by operational risk bucket instead of severity alone. During CVE rematch, duplicate source candidates for the same package finding are collapsed before insert, preferring higher CVSS, stronger severity, fixed-version data, richer titles, and primary references. Paginated API list endpoints clamp negative or excessive `limit`/`offset` values through `BONGSU_API_MAX_PAGE_LIMIT` and `BONGSU_API_MAX_PAGE_OFFSET` before reaching SQL. Filtered vulnerability views can be exported through `/api/vulnerabilities/export` as CSV by default or JSON with `format=json`. The export requires `export` or `admin` RBAC permission and reuses the same host, severity, triage status, finding source, risk level, exploited, EPSS, package, container, owner, team, environment, criticality, sorting, fixed-version, ecosystem-mismatch, and RBAC filters as the interactive vulnerability list. CSV and JSON rows include the host metadata, risk score/level, advisory sources, and package placement context fields so exported remediation queues can be routed outside bongsu; JSON exports include a metadata block with generation time, applied filters, row cap/truncation state, and `security_db_revision`, while CSV exports expose the same revision/truncation signals through response headers and audit metadata. CSV cells that could be interpreted as spreadsheet formulas are prefixed with a single quote before download. `BONGSU_VULN_EXPORT_MAX_ROWS` limits export size and defaults to 100000 rows. Export attempts are audited before bytes leave the service with follow-up success or error audit rows.

## Webhook Notifications

Operators can configure `BONGSU_WEBHOOK_URL` to receive outbound JSON webhooks for `scan.completed` and `security_db.updated`. `scan.completed` includes host identity, scan status, inventory status, package/container counts, inserted/skipped vulnerability row counts, ingest errors, vulnerability totals, severity counts, and computed risk-level counts; `security_db.updated` includes the update reason and `security_db_revision` used by the follow-up automatic rescan requests. `BONGSU_WEBHOOK_MIN_SEVERITY` controls the minimum severity that triggers scan notifications, `BONGSU_WEBHOOK_MIN_RISK_LEVEL` controls the minimum computed risk bucket that triggers scan notifications, and `BONGSU_WEBHOOK_INVENTORY_STATUSES` triggers notifications for selected SBOM health states such as `empty` or `degraded`. `BONGSU_WEBHOOK_SECRET` signs payloads with `X-Bongsu-Signature-256: sha256=<hex hmac>` for receiver verification. Delivery retries network failures, HTTP 429, and HTTP 5xx responses up to `BONGSU_WEBHOOK_RETRY_ATTEMPTS` with `BONGSU_WEBHOOK_RETRY_DELAY_MS` between attempts. Each attempt uses `BONGSU_WEBHOOK_TIMEOUT_SECONDS`, and retry delay/timeout values are clamped to bounded operational ranges so a bad environment value cannot create extremely slow or busy delivery loops. Webhook audit rows include the final HTTP status, attempt count, and security DB revision when present.
